## 一、网页投稿：CAPTCHA=0 不再 403（重点）

关闭验证码（`CAPTCHA=0`）时，前端 `loadCaptcha` 直接跳过取 token——而服务端
对每次提交都校验 HMAC 签名，token 为空串意味着**网页投稿 100% 返回 403**，
真实手机浏览器上的投稿链路整体不可用。修复后无论验证码开关如何，页面都会
先取"免答 token"再提交。人工真机验证清单见
[`REAL_DEVICE_VERIFICATION.md`](REAL_DEVICE_VERIFICATION.md)。

## 二、发布与审核链路一致性

- **发布状态机**：消息已发到群里后，收尾时的 D1 抖动不会再把 `published`
  覆盖成 `failed`（条件更新，failed 只能从 publishing 打过来）；
- **媒体投稿审核卡**：带图投稿的审核卡编辑此前走纯文本接口必然 400，现在
  文本卡/媒体卡各自走正确的编辑通道；
- **拒绝窗口竞态**：管理员输入拒绝理由期间投稿被并发发布，不会再留下
  「群里已公开、库里已拒绝」——拒绝统一走带守卫与作者通知的唯一实现；
- **长文案截断**：超长 HTML 不再把 `<b>`/`<a>` 标签切成两半导致 Telegram
  拒收、发布永远失败；
- **限流时钟**：限流清理与计数统一用同一只钟，消除计数随机归零。

## 三、安全加固

- **webhook 伪造封堵**：配置 `WEBHOOK_SECRET` 后，secret 头缺失或不匹配
  一律 403（常量时间比较）；未配置保持可用但启动自检强烈警告；
- **/health 深度自检**：除进程存活外增加 D1 可达性检查（存储故障返回 503）；
- **错误不回显**：后台审核接口不再把原始异常文本（可能含上游 URL/参数）
  返回给 HTTP 客户端；
- **限流防绕过**（二轮审计加固）：超大/chunked 请求体在解析**之前**就按 IP
  预检 429，纯消耗流量不再能强迫 Worker 读完全部字节；收件箱读端点与写
  操作共用限流桶（此前可零成本刷 D1 读取量）；
- **其余**：审核收尾状态回写 CAS 化、/setup 恒时比较、无主媒体消息清理、
  show_if 指向后置步骤直接部署报错、过期会话的全局兜底清理。
